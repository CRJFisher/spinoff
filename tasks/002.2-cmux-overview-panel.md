# cmux Overview Panel

An always-on dashboard that monitors all active spinoff agents, surfaces status via cmux's sidebar and desktop notifications, and provides interactive supervisor actions — all powered by cmux's `read-screen` capability that WezTerm lacks.

## Architecture

### Process model

The overview has two components running in a dedicated `spinoff-overview-{project_name}` cmux workspace:

1. **Poller process** — a Python `while True` loop (`python -m spinoff.overview watch`) in a terminal surface. Polls each agent's screen every 3–5 seconds, classifies status, writes HTML, updates sidebar metadata.
2. **Browser pane** — cmux's embedded browser displaying `.overview.html` via `file://` URL with `<meta http-equiv="refresh" content="5">` for self-refresh.

No web server. No asyncio. No daemon. The poller lives and dies with its cmux surface.

### Data flow

```
.state.json (structural truth: which worktrees exist)
      |
      v
  Poller loop (every 3-5s)
      |
      +---> cmux read-screen --surface <id> (per agent)
      |         |
      |         v
      |     Status classifier (regex on last 30 lines)
      |         |
      |         v
      +---> AgentSnapshot (in-memory, ephemeral)
      |         |
      |         +---> .overview.html (atomic write)
      |         +---> cmux set-status / set-progress (sidebar)
      |         +---> cmux notify (on state transitions)
      |
      v
  .overview-actions.json <--- browser JS writes action requests
      |
      v
  Poller reads, validates, executes, deletes
```

State file is the shared bus. No IPC between spinoff commands and the overview — `/spinoff:new` writes to state, the poller sees it on the next cycle (≤5s latency).

## Agent status detection

### States

| State      | Signal                                   | Detection                                                                                                  |
| ---------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `STARTING` | Script running, Claude not yet visible   | No Claude banner in output                                                                                 |
| `BUILDING` | Build command executing                  | Build tool output (`pnpm`, `cargo`, etc.) before Claude starts                                             |
| `WORKING`  | Claude actively generating               | Spinner chars (`⠋⠙⠹...`), tool-use box headers (`╭─ Bash ─╮`), no input prompt at bottom                   |
| `IDLE`     | Claude at prompt, waiting for next task  | Input prompt `>` visible, no completion phrases                                                            |
| `WAITING`  | Permission prompt or question            | `❯ Yes` / `Allow once` / `Do you want to proceed?` in bottom 15 lines                                      |
| `ERRORED`  | Build or Claude error                    | `Error:`, API errors, auth failures — only outside tool-result boxes, and only if no recovery prompt below |
| `DONE`     | Claude exited                            | `"Claude exited. Shell kept open."` (from spinoff's startup script)                                        |
| `SHELL`    | Bare shell (build failed or manual exit) | Bare `$` / `%` prompt, no Claude chrome                                                                    |
| `DEAD`     | Surface gone                             | `read-screen` returns error or surface missing from `list-workspaces`                                      |

### Classification approach

1. Call `cmux read-screen --surface <id> --lines 30` (last 30 lines, no scrollback by default)
2. Strip ANSI escape sequences
3. Strip tool-result box contents (between `╭─ ... Result ─╮` and `╰───╯`) to prevent false positives from error text inside tool output
4. Match ordered regex patterns (first match wins, priority: DONE > SHELL > WAITING > ERRORED > WORKING > BUILDING > IDLE)
5. Extract a 1-line snippet for display (tool name + first content line for WORKING, prompt text for WAITING, error line for ERRORED)

### Adaptive polling

| State             | Poll interval | Rationale             |
| ----------------- | ------------- | --------------------- |
| WORKING, STARTING | 1–3s          | Track rapid changes   |
| WAITING, ERRORED  | 3s            | Stable but actionable |
| IDLE, DONE, SHELL | 5–10s         | Nothing changing      |

After 3 consecutive identical reads, interval increases by 1s per read up to 10s max. State change resets to base interval.

## Data model

```python
class AgentPhase(Enum):
    STARTING = "starting"
    BUILDING = "building"
    WORKING = "working"
    IDLE = "idle"
    WAITING = "waiting"
    ERRORED = "errored"
    DONE = "done"
    SHELL = "shell"
    DEAD = "dead"

@dataclass
class AgentSnapshot:
    worktree_name: str
    phase: AgentPhase
    surface_id: Optional[str]
    snippet: str                       # last meaningful line for display
    error_message: str = ""
    cost_usd: Optional[float] = None   # parsed from Claude's status bar
    token_count: Optional[int] = None
    updated_at: float = 0.0           # time.monotonic()
```

Runtime snapshots are **in-memory only** inside the poller. If the poller dies, snapshots rebuild from screen content on restart. Nothing to persist.

## Notifications

### Tiers

| Transition     | Tier          | Sidebar       | Desktop | Flash |
| -------------- | ------------- | ------------- | ------- | ----- |
| `* -> WORKING` | silent        | Update status | —       | —     |
| `* -> WAITING` | **urgent**    | Update status | Yes     | Yes   |
| `* -> ERRORED` | **urgent**    | Update status | Yes     | Yes   |
| `* -> DONE`    | informational | Update status | Yes     | —     |
| `* -> IDLE`    | silent        | Update status | —       | —     |

### Fatigue prevention

- **Per-workspace cooldowns**: 30s between urgent notifications, 60s between informational
- **Batch window for DONE**: 5s delay collects simultaneous completions into a single notification ("3 agents done: fix-auth, feat-dark-mode, refactor-api")
- **Focus suppression**: skip desktop notification if the user is already focused on that workspace

### Sidebar metadata

```
cmux set-status --workspace <id> "working [4m]"
cmux set-status --workspace <id> "NEEDS APPROVAL [12m]"
cmux set-status --workspace <id> "done [23m]"
cmux set-progress --workspace <id> -1    # indeterminate pulse while working
cmux set-progress --workspace <id> 100   # full bar on done
cmux log --workspace <id> "[14:32] working -> WAITING"
```

### Configuration

Optional `notifications` block in `spinoff.json`:

```json
{
  "notifications": {
    "desktop": true,
    "flash": true,
    "on_done": true,
    "on_error": true,
    "on_waiting": true,
    "cooldown_urgent_secs": 30,
    "cooldown_info_secs": 60
  }
}
```

All fields optional, defaults shown above.

## Supervisor actions

### Available actions

| Action          | Trigger             | cmux command                                                 | Confirmation?        |
| --------------- | ------------------- | ------------------------------------------------------------ | -------------------- |
| Focus agent     | Click row           | `select-workspace --workspace <id>`                          | No                   |
| Approve prompt  | Click "Approve"     | `send --surface <id> y` + `send-key enter`                   | No                   |
| Reject prompt   | Click "Reject"      | `send --surface <id> n` + `send-key enter`                   | No                   |
| Interrupt agent | Click "Interrupt"   | `send-key --surface <id> ctrl-c`                             | No                   |
| Kill agent      | Click "Kill"        | `close-surface --surface <id>`                               | Yes (confirm dialog) |
| Restart agent   | Click "Restart"     | Close surface + `new-workspace` with existing startup script | Yes                  |
| Approve all     | Click "Approve All" | Iterate WAITING agents, re-read screen, apply safety filter  | Yes                  |

### Safety filter for approvals

Prompts matching these patterns are **never auto-approvable** (skipped by "Approve All", shown as "Review Required" in dashboard):

- `git push --force` / `git push -f`
- `rm -rf /` or recursive delete outside worktree
- `sudo` or privilege elevation
- `reset --hard`, `checkout .`, `restore .`, `clean -f`
- Credential/secret/token access patterns
- External network requests (non-localhost `curl`/`wget`)

### Browser-to-Python bridge

The HTML dashboard cannot call cmux directly. Instead:

1. JS writes a JSON action to `.claude/worktrees/.overview-actions.json`
2. Poller reads it on the next cycle, validates against schema + allowed action set + surface ID in state, executes, deletes
3. Schema: `{ action: string, surface_id: string, timestamp: number }` — reject if >30s stale

## Cross-agent coordination

### Dependency declaration

```
/spinoff:new consume-api --depends-on build-api
/spinoff:new integration-tests --depends-on build-api,consume-api
```

Stored in `WorktreeEntry.depends_on: list[str]`. Validated at creation time (referenced worktrees must exist, no cycles via topological sort).

### Completion context sharing

When agent A completes:

1. Poller detects DONE via `read-screen`
2. Extracts summary: `git log --oneline base..HEAD` + `git diff --stat base..HEAD` in the worktree
3. Stores summary in `WorktreeEntry.summary`
4. For each dependent agent B: writes context to `.claude/dependency-context/<dep-name>.md` in B's worktree

### Conflict detection

Each poll cycle: `git diff --name-only base...HEAD` per active worktree. Files touched by 2+ agents are flagged in the dashboard with "File Overlaps" section.

### Merge ordering

Topological sort of dependency graph produces merge layers:

```
Layer 1 (merge first): build-api, setup-db
Layer 2 (after layer 1): consume-api, migrate-data
Layer 3 (after layer 2): integration-tests
```

`/spinoff:merge` enforces this by default (error if unmet dependencies), with `--force` override.

### Rebase on merge

When agent A merges, active agents that depend on A are auto-rebased onto the updated base branch. Failed rebases are aborted and the agent is notified via `cmux send`.

### Error propagation

When agent A errors, dependent agents are paused (`status: "paused"`) and notified. When A recovers, dependents resume.

## Security model

### Privilege boundaries

The overview process runs unsandboxed (full host access). Agents run inside Claude Code's sandbox. Every overview capability is a potential escalation vector.

| Boundary                               | Mechanism                                                    |
| -------------------------------------- | ------------------------------------------------------------ |
| Overview never writes inside worktrees | HTML written to `~/.cache/spinoff/<project>/overview.html`   |
| No dynamic text injection              | Hardcoded send actions only (y/n/ctrl-c), no free-text input |
| No autonomous approval                 | Every send requires user click; no auto-approve in v1        |
| Dangerous prompts blocked              | Safety filter pattern matching on screen text                |
| Screen content not persisted           | Snippets redacted for secrets before writing to HTML         |
| Surface ID validated                   | Checked against state file before every send                 |
| Action files validated                 | Schema check, staleness check (30s), allowed action set      |
| Audit trail                            | JSONL log at `~/.cache/spinoff/<project>/overview.log`       |

### Secret redaction

Before writing snippets to HTML:

- `(sk-|pk_|Bearer |token=)[A-Za-z0-9_-]{8,}` -> `\1[REDACTED]`
- `(password|secret|key|token)\s*[=:]\s*\S+` -> `\1=[REDACTED]`
- Database connection URIs -> `[REDACTED]`

## Lifecycle

### Start

Auto-launches when the first agent is created (`ensure_overview_running()` called at end of `create.py::main()`). Idempotent — subsequent calls verify the overview is alive and no-op.

### State tracking

`.state.json` gains an `overview` section:

```json
{
  "worktrees": [...],
  "overview": {
    "workspace_id": "ws-abc123",
    "surface_id": "sf-def456",
    "pid": 94210
  }
}
```

### Crash recovery

- **Poller dies, workspace survives**: next `/spinoff:new` or `/spinoff:overview` restarts the poller into the existing workspace
- **Workspace closed**: everything recreated from scratch; all state re-derived from `read-screen` + `.state.json`
- **No persistent state needed**: screen content is re-polled, sidebar metadata is re-pushed

### Stop

Closes when the user closes the workspace or runs `/spinoff:overview --close`. Does NOT auto-stop when all agents finish (user may want to review/merge).

## Testing strategy

### Unit testing (no cmux required)

All screen parsing lives in pure functions (`overview/status.py`). All I/O goes through the injected `TerminalBackend` Protocol.

- **`test_status.py`** — screen classification with canned terminal output strings. Tests each state, priority ordering, false positive prevention (error-in-tool-result, error-with-recovery), ANSI stripping.
- **`test_renderer.py`** — HTML generation from `AgentSnapshot` lists. Snapshot assertions on output.
- **`test_poller.py`** — polling logic with a `FakeBackend` that returns canned `read_screen` responses.
- **`test_actions.py`** — action dispatch with a `SpyBackend` that records calls for assertion.
- **`test_backends_init.py`** — backend auto-detection with mocked `subprocess.run`.

### E2E testing

Parameterize existing e2e tests to run against both backends (when available). E2e conftest detects which backends are installed and skips appropriately.

## Phased implementation

### Phase 1 — Monitor + Notifications (MVP)

Build the terminal backend abstraction and polling core. No dashboard, no browser.

1. `spinoff/terminal.py` — Protocol with ~10 methods
2. `spinoff/backends/cmux.py` — cmux implementation
3. `spinoff/backends/wezterm.py` — refactored from `spinoff/wezterm.py`
4. `spinoff/overview/status.py` — screen parsing heuristics (pure functions)
5. `spinoff/overview/poller.py` — poll loop, state transitions, desktop notifications
6. Expand `WorktreeEntry` with `terminal_id`, `last_status`
7. Update `create.py` and `merge.py` to use backend abstraction

**Delivers**: desktop notifications when agents finish, error, or wait.

**Complexity**: Medium. **Risk**: Medium (`read-screen` reliability — spike first).

### Phase 2 — Dashboard + Sidebar + Actions

Build the visible overview panel on top of Phase 1's data.

1. `spinoff/overview/renderer.py` + `template.py` — HTML generation
2. `spinoff/overview/actions.py` — approve, kill, focus via action file bridge
3. Sidebar metadata integration (`set-status`, `set-progress`, `log`)
4. `spinoff/overview/__init__.py` — workspace creation, browser pane, lifecycle
5. `/spinoff:overview` skill

**Delivers**: single-glance view of all agents with interactive controls.

**Complexity**: Medium-large. **Risk**: Medium-high (cmux embedded browser — validate `file://` support early).

### Phase 3 — Intelligence Layer

Cherry-pick independently:

1. **Conflict detection** — `git diff --name-only` across worktrees
2. **Merge ordering** — topological sort of dependency graph
3. **Rebase triggers** — auto-rebase dependents on merge
4. **Auto-approve policies** — config-driven rules for safe prompts
5. **Cross-agent context sharing** — dependency summaries written to worktree files

**Complexity**: Large (aggregate). **Risk**: High.

### Pre-Phase 1 spike

Before writing production code: a 20-line script that creates a cmux workspace, runs a command, calls `cmux read-screen`, and verifies the output is usable. If `read-screen` is unreliable, the entire concept needs rethinking.
